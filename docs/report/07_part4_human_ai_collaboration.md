# 7 第四部分：人机协同思考

## 7.1 问题、数据与边界

本部分回答两个问题：在本研究的公开招聘样本中，哪些岗位任务更适合由 AI 自动化辅助；对于金融风险模型相关工作，应如何划分 AI 与人的职责。数据来自 `data/processed/jobs_clean.csv` 的 242 条去重后招聘记录，岗位名称、公司名称、技能要求以及来源工作表和行号均保留在结果中。评分单位为一条招聘记录，并按“公司-岗位名称”汇总为 222 个组合；没有增加、补写或改名任何岗位。

这里的“AI 替代风险”严格表述为**任务自动化潜力评分**。它是基于招聘文本的研究设计结果，不是某个人会被替代的概率，也不能推断整个职业或整个行业的就业变化。招聘文本未出现某个词，不等于该工作实际不需要该能力；岗位发布平台、地区、岗位类型和词典本身都会带来偏差。

## 7.2 七维透明评分设计

为避免使用不透明的主观总分，脚本只读取每条记录的“职位名称+技能要求”，采用固定词典逐项匹配，保留命中词作为证据。七项均映射为 1--5 分：0 个命中词为 1 分，1 个为 3 分，2--3 个为 4 分，4 个及以上为 5 分。词典在 `src/score_automation_risk.py` 中可直接审查和修改，运行后每条记录的命中词写入 `outputs/tables/ai_substitution_risk_job_level.csv`。

| 维度 | 对自动化潜力的方向 | 示例词典线索 |
| --- | --- | --- |
| 任务重复性 | 正向 | 录入、对账、测试、报表、脚本、监控 |
| 规则明确性 | 正向 | 流程、规范、标准、审批、SQL、指标 |
| 数据结构化程度 | 正向 | 数据库、数据仓库、ETL、统计、数据建模 |
| 复杂沟通需求 | 反向 | 客户、谈判、咨询、需求调研、售前、驻场 |
| 责任判断需求 | 反向 | 方案、架构、规划、策略、模型验证、复杂问题 |
| 合规或信任责任 | 反向 | 合规、监管、审计、反洗钱、征信、数据安全 |
| 跨部门协调需求 | 反向 | 协同、对接、项目管理、交付、跨团队 |

设前三项为正向得分 $P_i$，后四项为人类责任得分 $H_j$，则：

$$
\text{任务自动化潜力评分}=100\times\frac{\sum_{i=1}^{3}P_i+\sum_{j=1}^{4}(6-H_j)}{35}。
$$

评分范围为 0--100，67 分及以上记为“高”、34--66.9 分记为“中”、34 分以下记为“低”。该分类阈值仅服务于本研究中岗位的相对比较。

复现命令如下：

```bash
MPLBACKEND=Agg python3 src/score_automation_risk.py
```

## 7.3 评分结果与解释

242 条招聘记录的平均任务自动化潜力评分为 **61.8**。其中高分记录 56 条（23.1%）、中分记录 183 条（75.6%）、低分记录 3 条（1.2%）。结果首先反映的是本次岗位文本中“流程、结构化数据、重复任务”与“沟通、判断、责任”线索的相对组合，不能理解为 AI 可以直接承担完整岗位。

## 7.4 金融工程师的人类+AI协同流程

选择样本中的“金融工程师”作为流程场景锚点：天阳科技 `JOB_0163`（来源工作表 `9-12`、第 2 行）。该岗位文本要求数学与统计建模、金融风险模型验证、数据建模、沟通表达、团队协作和复杂问题分析。按照本节规则，它的评分为 48.6（中）。这支持“AI 增强而非岗位替换”的设计：AI 负责可验证的计算、比对和提示，人负责证据、例外、责任和最终决定。

下表是一个概念性工作流，不声称任何样本公司已经采用该流程。它对应教材第 3.7 节“人类与机器”的互补关系，并为金融场景保留人类问责和申诉通道。

| 步骤 | AI 可以执行的任务 | 必须由人负责的任务 | 控制与留痕 |
| --- | --- | --- | --- |
| 1. 任务受理与授权 | 检查资料字段完整性、识别缺失项、生成待补清单 | 确认业务目的、数据授权范围和适用政策 | 记录数据来源、授权人、处理目的和版本号 |
| 2. 数据准备 | 对已获授权的数据做格式校验、异常值提示、字段映射和去标识化建议 | 审批敏感字段使用；判断异常是业务事实还是数据错误 | 最小权限、脱敏规则、访问日志和数据质量报告 |
| 3. 模型与规则计算 | 执行已批准的风险模型、计算指标、检索相似历史案例、生成解释草稿 | 确认模型版本、适用范围和业务规则；禁止 AI 自行修改阈值 | 保存输入摘要、模型/规则版本、输出和置信提示 |
| 4. 异常识别与初步建议 | 标记超阈值、数据冲突、规则冲突和分布漂移；按证据排序 | 复核关键证据，判断例外情形与潜在偏差 | 异常队列、人工复核结论和复核理由 |
| 5. 风险结论与处置建议 | 汇总计算结果，生成可编辑的风险说明和情景比较 | 作出风险判断、确定处置方案；涉及授信、交易、合规处罚等高影响决定时必须由有权人员签署 | 人工签署、决策依据、必要的双人复核与升级规则 |
| 6. 对外沟通与申诉 | 辅助生成清晰说明、检索相关政策条款 | 向客户或业务部门解释结论，处理异议和申诉，承担沟通责任 | 对外版本留档、申诉记录、纠错时点 |
| 7. 反馈闭环 | 汇总人工纠正类型、监测错误率和漂移、提出规则或 Prompt 优化候选 | 审核是否采纳更新，组织偏差审查和定期复验 | 变更审批、离线测试记录、审计日志和回滚方案 |

此流程的红线是：AI 输出只能是分析材料或建议，不能自动作出高影响金融决定；模型或 Prompt 的更新必须经过人工审批和可追溯测试。第三部分的结果也说明了这一必要性：即使固定 JSON 格式并进行人工金标准评价，细粒度技能字段仍会出现抽取粒度差异，因此真实金融流程需要人工复核，而不是只凭模型输出执行。

## 7.5 面向金融专业学生的五条行动建议

1. **建立“Python + SQL + 数据质量”基本功。** 以数据编辑、数据分析、大数据开发等岗位出现的录入、数据处理、SQL、数据库和数据仓库要求为线索，完成一个可复现项目：用 SQL 完成查询与质量校验，用 Python 输出清洗日志、异常清单和图表，并把代码和数据字典一并保存。
2. **把金融业务知识练成可验证的模型判断。** 以 `JOB_0163` 中的金融风险模型验证要求为练习场景，学习统计建模、回测/验证、假设检验和情景分析；每次结论都写清数据范围、假设、失效条件与人工复核点，而不只提交一个分数。
3. **学习 Prompt 设计，也学习评测与复核。** 在第三部分的真实实验中，P3 的严格字段宏平均准确率最高（0.6744），P2 的跨轮稳定性最高（0.9583），但技能字段仍存在粒度不一致。实践时应为每个字段保留原文证据，抽样建立金标准，并把错误类型写入下一轮 Prompt 或规则改进表。
4. **把合规、隐私和数据治理当作技术能力。** 对涉及客户资料、征信、支付、风控或监管数据的分析，先完成数据最小化、脱敏、权限申请、版本记录和审计日志，再调用模型。可以用一份“数据使用与风险检查单”训练自己在项目开始前识别高影响决定。
5. **练习解释、协商和跨部门交付。** 本次低评分岗位普遍出现沟通、协调、客户、方案、需求分析或跨团队线索。每个数据/AI项目都应练习把技术发现转写成业务问题、备选方案、风险和责任人，并在汇报中接受非技术人员的追问。

## 7.6 局限性

1. 词典匹配只能识别招聘文本中显式出现的线索，不能完整识别隐含任务；不同写法会影响得分。
2. 每个公司-岗位组合常只有一条公开记录，排名用于案例比较，不能作为公司层面的统计结论。
3. 本研究讨论的是任务层面的可辅助性，不评估技术可行性、成本、组织采纳、劳动法规或实际裁员结果。
4. 协同流程为课程研究提出的治理设计，不代表任何公司既有制度；真实部署前还需要法律、合规、信息安全和业务负责人审查。
